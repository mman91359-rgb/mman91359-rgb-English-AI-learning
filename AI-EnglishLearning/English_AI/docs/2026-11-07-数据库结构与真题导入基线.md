# 数据库结构与真题/词库导入基线

- 日期：2026-11-07
- 范围：user_db / exercise_db / learning_db 实际结构、三条核心数据链路、英语资源盘点、导入落库方案、登录注册性能诊断
- 依据：Flyway 迁移文件 + 运行中 MySQL 实测（information_schema / COUNT）+ 运行中服务接口实测
- 结论均为实测，未做推测；不确定处已标注"待确认"

---

## 0. 结论速览

1. 三个库各归属一个服务，`user_db`（账号/金币/签到/偏好）、`exercise_db`（题库/词库/个人学习数据）、`learning_db`（遗忘曲线）。共 27 张业务表（10 + 16 + 1，不含各自 `flyway_schema_history`）。
2. **词汇练习不读 `word_dictionary`，读的是 `question_info`（module_type=1）**。仅导入词库不会产生练习题；且词汇模块的题型被 `ModuleType` 强制为 `FILL_BLANK`，题库里写 `CHOICE` 也会被按填空处理。
3. `question_info.external_key` 是导入幂等键，但只有 28/132 条有值（词汇 60、语法 40、听力 4 为空）。该列由 **`V1.0.2__add_listening_segment_fields.sql` 正式创建**（`ADD COLUMN` + `uk_external_key`），版本序在 V1.0.3 之前，因此**全新库可直接 migrate 到底，不存在缺列失败**；`sql/` 历史脚本里从未出现过这一列。缺口只剩存量回填，见 §6.1。
   > 更正（2026-11-07）：原结论"它不在 V1.0.0 迁移里、由 `sql/10` 手工加、全新库必在 V1.0.3 失败"经逐文件核对不成立——V1.0.2 与 V1.0.3 同一提交引入，容易漏看 ALTER 语句。
4. 词库资源可直接采：CET4 4901 条、CET6 1228 条 jsonl，含词头/英美音标/词性/释义/例句/短语，字段完整度高于现有 30 条种子。
5. 登录慢 ≈ 100% 由 BCrypt(cost=12) 构成：服务实测单次 0.42–0.49s，其余环节（MySQL 查询、网关转发、JWT）合计 9–10ms。注册 = 一次 encode + 前端紧接着一次 match，≈0.9–1.1s。

## 3. 关键约束与枚举（写导入脚本前必须遵守）

### 3.1 模块 → 默认题型 → 雷达维度

| module_type | 模块 | 强制题型 | 雷达维度 |
|---|---|---|---|
| 1 | 词汇 | FILL_BLANK | vocabulary |
| 2 | 语法 | SENTENCE_MAKING | grammar |
| 3 | 翻译 | TRANSLATION | reading |
| 4 | 听力 | CHOICE | listening |
| 5 | 造句 | SENTENCE_MAKING | grammar |
| 6 | 写作 | WRITING | 无（不更新雷达） |

来源：`common/ModuleType.java`。取题时 `questionType = ModuleType.defaultQuestionType(moduleType)` 覆盖库里的值 —— **词汇题只能是填空**。

### 3.2 选择题答案契约（`ChoiceAnswerUtil`）

- `options` 支持两种 JSON：数组 `["A. text","B. text",…]` 或对象 `{"A":"text","B":"text"}`。
- `correct_answer` 支持 `"A"` / `"A. text"` / 纯选项文本。
- 判对规则：用户提交字母或文本，归一化（去 `A.`/`A)`/`A、` 前缀、压空白、小写）后与正确选项比对。
- CHOICE 只走本地比对，不进 AI 语义判对链。

### 3.3 判题三级路由

L1 归一化精确比对（含 `accepted_answers` JSON 数组） → L2 短句翻译走 AI `/ai/judge-acceptable` 语义兜底（段落翻译不做） → L3 LLM 启发式反馈。`accepted_answers` 是"同义可接受答案"的唯一落库位置。

### 3.4 difficulty_level

1~8，同时是 ELO 的"题目难度分"。导入时必须给值，不能留 NULL（`NOT NULL`）。建议按源材料分档：词汇按词频序位（前 20% → 2~3，中段 → 4~5，尾段 → 6~7）。

### 3.5 逻辑删除

`question_info.is_deleted` 带 `@TableLogic`；导入脚本不要写 `is_deleted=1` 的行来"占位"，会被应用层过滤。

## 4. 三条核心链路

### 4.1 登录 / 注册

```
POST /user/login
  getByUsername(index uk_username)      ≈ 5 ms
  PasswordUtil.matches → BCrypt(12)     ≈ 420–490 ms   ← 全部耗时在这里
  updateById(last_login_at)             ≈ 3 ms
  JwtUtil.generate(HS256)               ≈ 1 ms
  radarService.getByUserId              ≈ 2 ms
```

注册：`getByUsername` → `BCrypt.encode(12)`（≈ 同量级）→ insert `sys_user` → insert `user_ability_radar` → 返回；前端 `RegisterView` 拿到结果后**自动调用一次 login**，再叠加一次 BCrypt match。

### 4.2 词汇新词练习

```
VocabQuizView
  → GET /exercise/vocabulary/new-questions?userId&count
  → ExerciseServiceImpl.selectNewVocabularyQuestions
      候选 = selectQuestions(userId, moduleType=1, count*2)   // 读 question_info + question_content
      过滤掉 user_vocabulary 里已存在的词（按 question.answerWord）
```

`word_dictionary` 只在两处被读：`getDailyWord`（按 `level` + `usage_count` 升序取一条）和词库管理。**它不参与练习选题。**

### 4.3 听力 / 翻译 / 写作

- 听力：`listening_audio`(audio_url + transcript) + `question_info`(module=4, CHOICE)，多段听力靠 V1.0.2 的分段字段。
- 翻译：module=3，`correct_answer` 存参考译文，长段落直接存 TEXT。
- 写作：`writing_essay` 独立表，题目侧 module=6 尚未导题。

## 6. 导入方案（分三阶段，逐阶段验收）

### 6.0 编码陷阱（写导入 SQL 前必读）

`V1.0.0__init_exercise_db.sql:245-259` 的 `word_dictionary` 中文注释是**乱码**：`鍗曡瘝`（单词）、`闊虫爣`（音标）、`绯荤粺鍗曡瘝璇嶅吀`（系统单词词典），第 249 行还留下不可逆的 `?`。成因是 UTF-8 字节被 GBK 解码后又按 UTF-8 写回，属于二次编码损坏。

- 后续任何生成迁移 SQL 的脚本必须显式 `writeFile(..., 'utf8')`，禁止依赖终端默认代码页（Windows 下常见 GBK）。
- 验收时 grep 乱码特征：`鍗|閲|璇|鏃|鐨|涓`，命中即视为导入失败。
- 已应用的 V1.0.0 不可修改；这些注释保持原样，只在新增文件里保证正确编码。

### 6.1 阶段 0（前置，必须做）：回填 `external_key`

**结论更正**：`external_key` 由 `V1.0.2__add_listening_segment_fields.sql:32-35` 正式创建（`ADD COLUMN` + `uk_external_key`），并非历史脚本手工添加；`sql/` 目录 `grep external_key` 为 0 命中。全新库 `migrate` 可从 V1.0.0 连续跑到 V1.0.8，**不会**在 V1.0.3 报缺列。

因此**不要**采用下面这两条旧方案，它们会制造新故障：

| 旧方案 | 实际后果 |
|---|---|
| 改 V1.0.0 补列 | 已有环境的 `validate-on-migrate=true` 会报 `Migration checksum mismatch for version 1.0.0`，必须先 `repair` |
| 新增 V1.0.8 加列 | 全新库在 V1.0.2 已加过，报 `Duplicate column name`（MySQL 8 无 `ADD COLUMN IF NOT EXISTS`） |

真正的缺口只有**存量 104 条 NULL**（词汇 60 + 语法 40 + 听力 4）。MySQL 唯一索引允许多个 NULL，不影响运行，只影响导入幂等。落地方式：

- 新增 `V1.0.8__backfill_external_key.sql`，**纯 DML**，`WHERE external_key IS NULL` 保证幂等；
- 键名用 `seed-{vocab|grammar|listening}-{cet4|cet6}-{两位序号}`，与 V1.0.3 的 `cet6-*`、V1.0.6 的 `translation-*` 以及将来导入的 `vocab-*` 天然分开；
- 已有的 28 条（听力 18 + 翻译 10）保持原值不动。

### 6.2 空库 baseline 陷阱（新发现，比缺列更真实）

`scripts/flyway.sh` 的 baseline 分支把版本固定为 `1.0.0`。对**空库**误执行 `baseline`，Flyway 只写一条历史记录、不执行 V1.0.0；随后 `migrate` 从 V1.0.1 开始，在 `V1.0.1__seed_core_data.sql:4` 的 `INSERT IGNORE INTO word_dictionary` 上报 `Table 'exercise_db.word_dictionary' doesn't exist`（`INSERT IGNORE` 不会忽略"表不存在"）。

- 空库只能 `migrate`；`baseline` 只用于"已有表结构、无 `flyway_schema_history`"的存量库。
- 已在 `scripts/flyway.sh` 增加空库检测：`flyway:info` 输出含 `Empty Schema` 时拒绝 baseline。

### 阶段 1：词库导入 → `word_dictionary`

源：`english-vocabulary-master` 的 CET4/CET6 jsonl（合计 6129 条，按 `word` 去重后预计 ~6000）。

| 目标列 | 来源 | 转换规则 |
|---|---|---|
| `word` | `headWord` | 小写去空格；唯一键，冲突即跳过 |
| `phonetic` | `content.word.content.ukphone` | 统一包成 `/…/`；无英音则用 `usphone` |
| `pos` | `trans[].pos` | 归一化：n / v / adj / adv / prep / conj / pron / num / int；多词性取第一个 |
| `translation` | `trans[].tranCn` | 多词性拼接为 `n. 电池；v. 充电`，长度 ≤ 200 |
| `example` | `sentence.sentences[0].sContent` | 无例句留空，**不生成** |
| `example_translation` | 同上 `.sCn` | 同上 |
| `level` | 来源文件 | `CET4` / `CET6` |
| `usage_count` | — | 0 |

产出：脚本 `scripts/import-words.mjs`（复用 `import-listening.mjs` 的"解析 → 校验 → 生成迁移 SQL → 落 pending 目录"范式），按等级拆两个迁移 `V1.0.9__seed_word_cet4.sql`、`V1.0.10__seed_word_cet6.sql`，每批 500 行，`INSERT … ON DUPLICATE KEY UPDATE`。

预计体量：CET4 约 3.5–4.5MB、CET6 约 0.9–1.2MB SQL 文本，单事务可接受。

### 阶段 2：词汇题生成 → `question_info` + `question_content`

这是"导入单词后真的能刷题"的关键一步，因为练习只认题库。

- `external_key`：`vocab-{level}-{序号}`（与阶段 1 共用词条序号，便于回溯来源）。
- `module_type=1`、`question_type=FILL_BLANK`、`target_level`、`difficulty_level` 按词频分档、`source='IMPORT'`、`ai_generated=0`、`usage_count=0`。
- 题干策略（按优先级，**不允许编造**）：
  1. 词条有例句 → 用例句挖空目标词：`He ___ his plan to travel.`，`correct_answer = abandoned`。
  2. 无例句 → 用释义挖空：`v. 放弃；抛弃 → ___`，`correct_answer` 为词形，`accepted_answers` 收同义变体（如 `abandoned/abandoning` 需谨慎，仅收该词形态）。
- `analysis` 写"音标 + 释义 + 例句翻译"，不要 AI 生成的长篇解释。
- 一题一 `question_content`，`question_info` 与 `question_content` 用 `question_id` 关联；批量插入时先插 info 拿到 id，再插 content（或按 external_key 反查）。
- 校验：生成后跑一次 `COUNT(*)` 对比，抽样 20 题走一遍真实答题接口，确认 `answerWord` 能被 `new-questions` 正确取到。

#### 前端契约（强制，不满足则题面显示异常）

| 契约 | 依据 | 要求 |
|---|---|---|
| `stem` 必须含 `___`（2 个以上下划线）| `frontend/src/views/VocabQuizView.vue:555` `blankRegex = /_{2,}\|\[BLANK\]\|\.{3,}/g` | 无占位符会退化成"整句 + 空输入框" |
| `analysis` 必须含中文全角括号 `（释义）` | `VocabQuizView.vue:531` `/[（(]([^）)]+)[）)]/g` | 括号内文本被渲染成中文高亮段 |

## 7. 登录 / 注册性能诊断

### 7.1 实测数据（本机，2026-11-07）

| 场景 | 耗时 | 备注 |
|---|---|---|
| `POST /user/login`（网关 8086） | 758ms（冷启首次）/ 480–500ms（稳定） | 冷启含 JIT + Hikari 建连 |
| `POST /user/login`（直连 8081） | 474–536ms | 网关无额外开销 |
| 用户不存在（跳过 BCrypt） | **9–10ms** | 只做一次索引查询 |
| 用户存在 + 密码错误（走 BCrypt） | 458–536ms | 与正确密码同量级 |
| 用户存在 + 密码正确 | 474–508ms | — |
| `GET /exercise/stats/{uid}` | 32ms（payload 22KB） | 登录后前端阻塞等待 |
| `GET /user/coin/info/{uid}` | 72ms | 登录后前端阻塞等待 |
| `GET /user/preference/{uid}` | 17ms | 登录后前端阻塞等待 |
| 3 个登录并发 | 各 410–436ms | 不串行，纯 CPU 并行 |
| GC（YGC 13 次累计） | 0.048s | 无 GC 压力 |
| 独立 JVM 基准 `BCrypt(12)` | 213–240ms（encode / match 同量级） | 同版本 jar、同 JDK17 |

**结论**：登录耗时 98% 是 BCrypt 计算；DB、网关、JWT、GC 全部可忽略。服务进程内的单次 BCrypt（420–490ms）比独立 JVM 基准（213–240ms）慢约 2 倍，属进程运行环境差异（IDEA 启动的子进程 + 低功耗 U 调度），不是代码问题——所以"这条 SQL 慢不慢"没有讨论价值，唯一变量是哈希强度。

### 7.2 注册为什么更慢

`RegisterView` 提交成功后自动调用 login：

```
BCrypt.encode(12)  ≈ 0.45s
+ BCrypt.matches(12) ≈ 0.45s
+ stats/coin/preference 阻塞 ≈ 0.07s
≈ 0.97s，弱机 1.1s+
```

而且 `userStore.login()` 里这三个接口是 `await` 后才 `router.push`，所以按钮转圈时间包含它们。

### 7.3 可选方案对比

| 方案 | 改动 | 预计效果 | 代价 |
|---|---|---|---|
| **A. BCrypt 强度 12 → 10** ✅ 已采用 | `common/PasswordUtil.java:11` + `UserServiceImpl.login` 重编码 + CLAUDE.md 条款 | 登录 ≈0.48s → **0.13s** | 抗离线爆破强度下降（OWASP 现推荐 10 即可）。**注意**：`BCryptPasswordEncoder.upgradeEncoding()` 只在存量强度低于目标时返回 true，降强度场景永远 false，必须自行比较 `BCrypt.getRounds()` 才能让存量 `$2b$12$` 也被重编码 |
| **B. 注册接口直接签发 token** | `UserServiceImpl.register` 返回 token，前端不再二次 login | 注册 ≈0.97s → **0.5s**，省掉整整一次 BCrypt | 需改注册响应契约与前端 store，属功能改动 |
| **C. 前端解耦登录后的拉取** ✅ 已采用 | `stores/user.ts` 的 `login` 改为 `void loadUserStats()/loadUserExtras()`，新增 `statsLoaded` 标志 | 体感 −70ms，且未来 stats 变重不再拖登录 | 首页首屏可能短暂显示 0，用 `coinLoaded`/`preferenceLoaded`/`statsLoaded` 兜底 |
| D. 关掉 MyBatis `StdOutImpl` SQL 日志 | `application.yml` 的 `log-impl` | 每次请求少几十行同步 console IO | 失去 SQL 调试输出 |
| E. 确认运行环境 | 用 `java -jar` 而非 IDE Run 复测 | 可能省掉 2 倍 BCrypt 环境损耗 | 仅影响本地开发体验 |

**推荐组合：A + C**（改动最小、收益最大，且不改变注册接口契约）。若不愿动安全参数，则退而求其次做 **B + C**，把注册压到 0.5s 左右。

### 7.4 顺带发现的隐患（建议排期，不在本次改动）

1. `getUserStats` 用 `selectList` **全量捞该用户所有答题日志**再在内存里跑 365 天循环 + 12 个月循环，且这个接口挂在登录链路。当前 219 条日志 → 32ms；涨到 5 万条会到秒级，表现为"登录越用越慢"。应改为 SQL 聚合（按日期 `GROUP BY`）+ 只回传需要的粒度。
2. `sys_user.phone` 无索引，手机号找回密码是全表扫描，用户量上千后是隐患。
3. `daily_word.date` 全局唯一 → 全站每天只有一个词，与"每人每日 N 词"的产品预期不同，导入大词库也改变不了这一点。
4. 业务实体 `QuestionInfo` 没有映射 `external_key` 字段，应用层不读不写它。靠 SQL 导入没问题，但如果之后想在管理端按 `external_key` 去重/追溯，需要补字段。
