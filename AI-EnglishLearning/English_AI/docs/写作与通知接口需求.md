# 写作与通知接口需求（C-1）

> 性质：**前端对后端的接口需求规格**，不是后端已实现的能力清单。
> 下面的接口路径与字段是前端提出的建议形态，需后端确认后再定稿；未确认前不得当作既有接口调用。
> 前端侧现状（用什么在顶、在哪个文件顶）全部实测列出，便于区分「已有接口但没接线」和「完全没有后端」。

## 0. 三项缺口的共同点

三项都是「前端已经在用、但底下没有真实后端」的功能，靠静态数组与 localStorage 顶着：

| 能力 | 现在靠什么 | 位置 |
|---|---|---|
| 写作题库 | 静态数组 `WRITING_TOPICS`，直接当缓存返回 | `api/writing.ts:15`、`mocks/writing.ts` |
| 写作草稿 | localStorage，键 `recall:writing:{userId}:drafts` | `api/writing.ts:44-96` |
| 写作收藏 | localStorage，键 `recall:writing:{userId}:favorites` | `api/writing.ts:102-111` |
| 通知列表 | localStorage，键 `notifications` | `useNotifications.ts:72-82` |
| 通知产生 | 前端自己判断并 `add()` | `useNotifications.ts:106-128`、`:136-154` |
| 题目来源 | 用 `groupKey.startsWith(...)` 猜 | `ListeningQuizView.vue:317-321` |

写作的**提交与评分**已经有真实后端（`/exercise/writing/submit`、`/submission/{id}`、`/submissions`、`/rescore`），缺的只是题库、草稿、收藏这三块的持久化。

## 1. 写作：题库 / 草稿 / 收藏

### 1.1 现状细节

- `fetchWritingTopics()` 直接 `Promise.resolve(TOPIC_CACHE)`，题库是打进包里的常量，改题要改代码重新发布。
- 草稿与收藏都以 `userId` 分区存在浏览器本地：换设备、换浏览器、清缓存全部丢失；同一账号两台机器看到不同的草稿。
- `setFavorite` 只写 localStorage，无任何服务端交互，所以「我的收藏」实际是「这台电脑上的收藏」。

### 1.2 建议的接口

| 用途 | 方法 | 路径（建议） | 入参 | 出参 |
|---|---|---|---|---|
| 题目列表 | GET | `/exercise/writing/topics` | `level`、`type`、`page`、`size`（均可选） | `WritingTopic[]` |
| 读草稿 | GET | `/exercise/writing/draft/{topicKey}` | —（userId 由网关透传） | `WritingDraft \| null` |
| 存草稿 | PUT | `/exercise/writing/draft/{topicKey}` | `content`、`elapsedSeconds` | `WritingDraft` |
| 删草稿 | DELETE | `/exercise/writing/draft/{topicKey}` | — | 空 |
| 草稿列表 | GET | `/exercise/writing/drafts` | — | `WritingDraft[]` |
| 收藏列表 | GET | `/exercise/writing/favorites` | — | `string[]`（topicKey 数组） |
| 加/取消收藏 | POST | `/exercise/writing/favorites` | `topicKey`、`favorite: boolean` | 空 |

### 1.3 字段对齐

`WritingTopic` 前端已有完整定义（`types/writing.ts:13-27`），后端按同一形状返回即可：
`id`、`type`、`level`、`title`、`directions`、`topic`、`requirements[]`、`wordRange[2]`、`timeLimitSeconds`、`source`、`outlineHints[]`、`usefulExpressions[]`。

`WritingDraft` 只需四个字段：`topicId`、`content`、`updatedAt`、`elapsedSeconds`
（`wordCount` 由前端 `countWords()` 现算，不要后端下发，避免两侧分词口径不一致）。

> **一致性要求**：同一个 `topicKey` 在题库、草稿、收藏、提交四处必须同名。现有提交接口用的字段名是 `topicKey`（`api/writing.ts:181`），而前端类型里叫 `topicId`，这对命名不一致需要在接后端时统一，建议以 `topicKey` 为准，前端改注释不改值。

## 2. 通知

### 2.1 现状细节

- 全量存在 localStorage，最多保留 50 条（`useNotifications.ts:123`）。
- 通知文案存的是 **i18n 键**（`titleKey` / `contentKey`）加参数，渲染时用 `$t` 翻译。
- 「成就通知」是前端在答题后自己判的：读 `lastExerciseResult`，`correctCount >= 10` 才 `add()` 一条（`useNotifications.ts:136-154`）。这个判断本应在后端做，因为答题结果只有后端有全量数据。

### 2.2 必须先定的一件事：后端下发文案还是下发 key

这是这份契约里唯一需要**先拍板**的设计问题，它决定了接口形态，不能边做边定：

| 方案 | 后端返回 | 优点 | 代价 |
|---|---|---|---|
| **A. 下发 key + 参数** | `titleKey: 'notification.achievementTitle'`、`params: {count: 10}` | 中英双语自动正确；前端可随时改文案不用后端发版 | 后端每加一种通知类型，前端必须同步加 i18n 条目，否则显示原始 key |
| **B. 下发已渲染文案** | `title: '连续答对 10 题，解锁成就'` | 后端自由加类型，前端零改动 | 英文界面会显示中文（或后端要按 `Accept-Language` 下发双语字段） |

**前端倾向 A**，理由：现有 `useNotifications` 与 `TopAppBar` 已经按 key 渲染，切到 B 要改渲染链路与全部已有文案；而且 A 天然满足双语。

但 A 有个前提要后端接受：**通知类型的枚举必须两端共同维护**。建议后端在 `notification` 表里存 `type` 与 `params`，前端维护 key 映射表，新增类型时两边同时加，漏加会显示原始 key（显性出错，比静默显示中文好）。

如果后端坚持 B，则要求返回 `titleZh` / `titleEn` 两个字段，前端按当前语言择一，不接受单语。

### 2.3 建议的接口

| 用途 | 方法 | 路径（建议） | 入参 | 出参 |
|---|---|---|---|---|
| 列表 | GET | `/user/notifications` | `page`、`size`、`unreadOnly` | `{ items, total, unreadCount }` |
| 未读数 | GET | `/user/notifications/unread-count` | — | `{ count: number }` |
| 标记单条已读 | POST | `/user/notifications/{id}/read` | — | 空 |
| 全部已读 | POST | `/user/notifications/read-all` | — | 空 |
| 清空 | DELETE | `/user/notifications` | — | 空 |

归属服务建议放 `user-service`（通知是用户维度，与 user_db 同库便于事务）。

### 2.4 数据结构建议

```
notification
  id            BIGINT PK
  user_id       BIGINT      -- 收件人
  type          VARCHAR(32) -- system / reminder / achievement / level
  title_key     VARCHAR(64) -- 方案 A 用
  content_key   VARCHAR(64)
  params_json   JSON        -- 渲染参数，如 {"count":10,"accuracy":0.8}
  is_read       TINYINT
  created_at    DATETIME
  is_deleted    TINYINT     -- 全局逻辑删除约定
```

## 3. 题目来源标签 sourceLabel

### 3.1 现状（这是最典型的「靠猜」）

`ListeningQuizView.vue:317-321`：

```
const group = currentQuestion.value?.groupKey || ''
const exam = group.startsWith('cet6-2022-12-1') ? '2022.12 CET6' : t('listening.practiceTitle')
return `[${t('listening.source')}] ${exam} · ${typeLabel(...)}`
```

**只有一组 `groupKey` 前缀能被识别**，其余全部退化成「听力练习」。这既是硬编码，也是漏标：题库里其他年份的真题全被显示成非真题。

另外 `translation.sourceLabel`（`zh-CN.ts:905`）是**翻译方向**（中译英），与本题指的不是一件事，不要混用。

### 3.2 需要后端做的

在题目数据里返回结构化来源，而不是让前端从 `groupKey` 字符串里拆：

```
source: {
  exam: 'CET6' | 'CET4' | null,   // null 表示非真题
  year: 2022,
  month: 12,
  paper: 1,
  label: '2022.12 CET6 第一套'      // 可选，后端拼好，前端直接显示
}
```

若后端不想维护结构，退一步只需给一个 `sourceLabel: string | null`，`null` 时前端显示当前 i18n 的「练习」文案。**但必须由后端给，不能前端从 `groupKey` 猜。**

## 4. 后端开工清单

### 4.1 数据表（4 张新表）

| 表 | 库/服务 | 说明 |
|---|---|---|
| `writing_topic` | exercise_db / exercise-service | 题库；`topic_key` 唯一键 |
| `writing_draft` | exercise_db | 草稿；`(user_id, topic_key)` 唯一键，防重复插入 |
| `writing_favorite` | exercise_db | 收藏；`(user_id, topic_key)` 唯一键 |
| `notification` | user_db / user-service | 通知；索引 `(user_id, is_read, created_at)` |

### 4.2 Flyway 迁移

按 `docs/数据库迁移规范.md`，新增 `V1.0.x__描述.sql` 到对应模块的 `db/migration/`，**不得修改已应用迁移**。
草稿表与收藏表的唯一键必须在迁移里建，不能靠应用层去重（并发下会插重）。

### 4.3 网关路由

- `/exercise/*` 已路由到 exercise-service，写作三个新接口无新增路由
- `/user/notifications*` 需确认 `api-gateway` 的 `/user/**` 路由覆盖到；`/user/notifications` 不在白名单，需鉴权（透传 `X-User-Id`）

### 4.4 业务错误码

后端已建 `BizCode`（通用 / user / admin / exercise / learning / ai 五段）。本需求需补：

| 建议新增 | 段 | 语义 |
|---|---|---|
| `TOPIC_NOT_FOUND` | exercise（038） | 提交/收藏的 topicKey 不存在 |
| `DRAFT_SAVE_FAILED` | exercise（039） | 草稿写入失败（区别于参数非法） |
| `NOTIFICATION_NOT_FOUND` | user（018） | 标记已读时 id 不存在 |

现有可复用的：`PARAM_INVALID`、`RESOURCE_NOT_FOUND`、`STATE_CONFLICT`、`OWNERSHIP_DENIED`。

### 4.5 明确不在本需求内

- 不改 ELO、遗忘曲线、判题引擎
- 不做通知的推送（WebSocket / 站内长连接），只做拉取
- 不做题库的后台增删改（那是管理端已有能力，另议）
- 不引入 Redis、MQ 等未在技术栈内的中间件

## 5. 前端落地路径（后端就绪后）

1. `api/writing.ts` 的 `fetchWritingTopics` / `fetchDraft` / `saveDraft` / `setFavorite` 改成调接口，**保留 localStorage 作为离线兜底**（断网时仍能写草稿），加同步标记
2. `useNotifications.ts` 的 `loadFromStorage` 改为首次拉取接口，本地只做缓存；`add()` 保留但仅用于前端自己的即时提示，不再当作持久化路径
3. 删除 `ListeningQuizView.vue:319` 的 `groupKey.startsWith` 判断，改读后端 `source`
4. 三处改动都**不新增 npm 依赖**，沿用现有 axios 封装

## 6. 验收口径

- 换浏览器登录同一账号，草稿与收藏一致
- 断网时能写草稿，联网后能合并，不丢最新版本
- 未读红点与后端 `unread-count` 一致，标记已读后立即归零
- 题库里任意一组真题都能正确显示来源，不再出现「全显示成练习」
- 英文界面下通知文案为英文（方案 A），或由后端下发按语言择一（方案 B）
