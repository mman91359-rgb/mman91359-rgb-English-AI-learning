## 1. 统一响应体

所有对外接口返回 `Result<T>`：

| 字段 | 含义 |
|---|---|
| `code` | **HTTP 语义**：200 / 400 / 401 / 403 / 404 / 405 / 409 / 429 / 500 |
| `message` | 可直接展示的中文 |
| `data` | 业务数据 |
| `traceId` | 8 位追踪号 |
| `bizCode` | **业务错误码**，成功时为 `null` |

约定：

1. `code` 的语义不因引入 `bizCode` 而改变。前端可以只按 `code` 做通用处理，也可以按 `bizCode` 精确区分。
2. 禁止把业务原因塞进 `code`（例如用 `code: 4001` 表示"余额不足"）。
3. 禁止裸返回 `List` / `String` / `Map`。
4. 成功一律 `Result.success(data)`；失败一律 `throw new BusinessException(...)`，由 `GlobalExceptionHandler` 统一转 `Result`。

## 2. HTTP 码（`ErrorCode`）

8 个成员：`BAD_REQUEST(400)` `UNAUTHORIZED(401)` `FORBIDDEN(403)` `NOT_FOUND(404)` `METHOD_NOT_ALLOWED(405)` `CONFLICT(409)` `TOO_MANY_REQUESTS(429)` `INTERNAL_ERROR(500)`。

**禁止**在 `Result.error(...)` 中写数字字面量。需要新状态码时，先加 `ErrorCode` 成员再引用。

## 3. 业务码（`BizCode`）

29 个，按域分段，段内连续。号码一旦上线不得复用；新增码在对应段末追加，并同步前端。

| 段 | 范围 | 成员 |
|---|---|---|
| 通用 | 001-009 | `PARAM_INVALID(1)` `OWNERSHIP_DENIED(2)` `RESOURCE_NOT_FOUND(3)` `STATE_CONFLICT(4)` `UNAUTHENTICATED(5)` `RATE_LIMITED(6)` |
| user | 011-019 | `USER_NOT_FOUND(11)` `ACCOUNT_DISABLED(12)` `PASSWORD_TOO_WEAK(13)` `PHONE_NOT_BOUND(14)` `PHONE_MULTI_ACCOUNT(15)` `VERIFY_CODE_INVALID(16)` `MOCK_CODE_LOCAL_ONLY(17)` `NOTIFICATION_NOT_FOUND(18)` |
| admin | 021-029 | `ACTIVITY_STATE_INVALID(21)` `NOTICE_STATE_INVALID(22)` `TIME_RANGE_INVALID(23)` `LAST_ADMIN_REQUIRED(24)` `SELF_OPERATION_DENIED(25)` `ROLE_INVALID(26)` |
| exercise | 031-039 | `QUESTION_NOT_FOUND(31)` `MODULE_MISMATCH(32)` `QUESTION_TYPE_INVALID(33)` `ANSWER_REQUIRED_FIRST(34)` `REVIEW_STATE_CONFLICT(35)` `WORD_BOOK_NOT_FOUND(36)` `ESSAY_NOT_FOUND(37)` `TOPIC_NOT_FOUND(38)` `DRAFT_SAVE_FAILED(39)` |
| learning / ai | 041-049 / 051-059 | 预留，暂未定义 |

用法：

- `new BusinessException(BizCode.X)` —— HTTP 与文案都取业务码内置值
- `new BusinessException(BizCode.X, "更具体的文案")` —— 只覆盖文案，HTTP 仍取内置值
- `Result.error(BizCode.X)` / `Result.error(BizCode.X, "文案")` —— 同上

每个 `BizCode` 内置一个 `ErrorCode`。改内置 HTTP 语义等于改线上行为，**必须评估前端影响**。

## 4. 豁免清单（不纳入 `Result` 统一约束）

| 豁免项 | 位置 | 理由 |
|---|---|---|
| SSE 流式 | `AiController.chat` / `AiController.score` | `SseEmitter` 是流式协议要求，无法包装 |
| 裸 `Map` ×3 | `AiController.judgeFeedback` / `judgeAcceptable` / `translateScore` | 服务间内部接口（ai-service ← exercise-service），契约以字段为准而非外层包装；包装需同步改 `TranslationScoreClient` 与 `JudgmentEngineImpl` 共 4 个调用点，且这三处都在 `try/catch(Exception)` 内，漏改只会静默回落本地判定而不报错 |

门禁对这 5 项按方法名白名单放行。

## 5. 已知例外（保留旧写法）

| 位置 | 现状 | 原因 |
|---|---|---|
| `AdminUserServiceImpl` 2 处 | `ErrorCode.BAD_REQUEST + 文案` | 若改 403，`frontend/src/api/admin.ts` 的 `getAdminErrorKey` 会把 403 一律映射成 `adminConsole.error.forbidden`（"无权限"），盖掉"不能修改自己的账号状态"这句具体文案。**根因在前端粗暴覆盖后端 message，修前端比改后端更对** |
| `VerificationCodeServiceImpl.badRequest(String)` | 私有工厂，14 个调用点 | 调用点语义横跨「参数非法 / 验证码错误 / 限流 / 未登录」四类，拆工厂会连带改 14 处 HTTP 语义（400 → 401 / 429） |

## 6. 门禁

两个脚本，均在 `English_AI/` 目录执行，只读，退出码 0 才算通过。

```bash
node scripts/check-backend-contract.mjs [--verbose]   # 响应体一致性
node scripts/check-migrations.mjs [--verbose]         # Flyway 迁移规约
```

### 6.1 响应体一致性

扫所有 `@RestController` 的接口方法，返回类型必须是 `Result<...>`。`SseEmitter` 与 3 个裸 `Map` 按方法名白名单放行（见 §4）。

**局限**：按 `@XxxMapping` 注解 + 方法签名正则解析，不做 AST。方法返回类型写在多行、或用别名 import（`import ...Result as R`）时会漏判。

### 6.2 Flyway 迁移规约

四条：

1. 文件名必须匹配 `V<大>.<中>.<小>__snake_case.sql`
2. 同模块版本号不得重复
3. 同模块版本号必须从 `1.0.0` 起连续递增（按数值排序，不按字典序）
4. `sql/` 根目录的手工脚本作为「第二变更渠道」列出提示（不 fail）

**局限**：只校验文件名与版本号，不校验 SQL 内容。`sql/` 下 15 个手工脚本（`02-add-favorites` ~ `11-admin-module` + `03b-fix-phonetic`，无 `01`）与 Flyway 并存，属历史遗留，归档计划见 Backlog。

### 6.3 双向实验要求

新增或修改门禁后，**必须**验证它真能抓：注入一处违规 → 确认 `exit 1` 且报出准确位置 → 还原 → 确认 `exit 0`。否则"0 违规"可能只是脚本没扫到。

两个门禁已于 2026-11-21 完成双向实验：

- 响应体：注入裸 `Map` 后精确报出 `ListeningController.java:60/71/85`，还原归零
- 迁移：注入跳号 + 命名错误后报出「缺 1.0.59」与「命名不合规」，清理归零

### 6.4 代码规约三条（`scripts/check-backend-rules.mjs`）

扫 327 个 java、27 个 `@RestController`、134 个接口方法。三条规则：

| 规则 | 判定 | 现状 |
|---|---|---|
| R1 | 带 `@RequestParam ... userId` 的 Controller 方法，方法体必须出现 `requireOwnership(` | 20 个方法，**20 个已校验**，0 违规 |
| R2 | Controller 方法体不许出现 `SELECT ... FROM` / `INSERT INTO` / `UPDATE ... SET` / `DELETE FROM` | 0 处 |
| R3 | 全仓不许 `new RestTemplate()`（必须注入） | 0 处 |

**R1 是这条门禁的核心价值**：现存 20 处 `@RequestParam Long userId` 全部已调 `requireOwnership`，所以现在建门禁不是清存量，而是防未来——C-1 要新增 8 个接口，新增时漏写校验会被直接拦住。

**注意口径**：`UserIdentityUtil.isForbidden` 在 `headerUserId == null`（本地直连无网关）时放行。所以 R1 校验的是「有没有调校验函数」，不是「有没有漏洞」——本地直连场景下 header 为空本来就不限制。

**与 `AGENTS.md` 的一处冲突已澄清**：`AGENTS.md` 明确「服务间调用：RestTemplate 直连（无 OpenFeign）」，所以「不许绕过网关直连」不能做成门禁，那是既定架构。R3 只禁 `new RestTemplate()`（自建实例），不禁注入式直连。

**双向实验**：注入 `requireOwnership` 改名 → R1 报出 `ListeningController:41`；注入 SQL 字符串 → R2 报出同一行；注入 `new RestTemplate()` → R3 报出 `UserController:47`。三处还原后均 `exit 0`。

**局限**：R1 按「方法签名含 query userId + 方法体含 `requireOwnership(`」判定，方法体通过括号配对截取。若把校验提取到私有方法里间接调用，会漏判；R2 只认大写 SQL 关键字，小写或拼接的 SQL 抓不到。
