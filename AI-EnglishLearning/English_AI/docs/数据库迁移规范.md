# Recall·睿考 数据库迁移规范（Flyway）

**建立时间**：2026-10-31
**适用**：user-service / exercise-service / learning-engine-service
**目标**：结构变更可追溯、可重放、可部署；禁止手工改共享库结构后不做记录。

## 1. 目录与版本

| 服务 | 数据库 | 迁移目录 |
|---|---|---|
| user-service | user_db | `user-service/src/main/resources/db/migration` |
| exercise-service | exercise_db | `exercise-service/src/main/resources/db/migration` |
| learning-engine-service | learning_db | `learning-engine-service/src/main/resources/db/migration` |

- 当前基线：
  - `V1.0.0__init_*.sql`：2026-10-31 当前完整结构快照（26 张业务表）。
  - `V1.0.1__seed_*.sql`：幂等种子（词库/题库/听力/欢迎通知），不含用户个人数据。
- 后续版本从 `V1.0.2` 开始递增。
- 文件名格式：`V<主>.<次>.<修订>__简短英文或拼音描述.sql`，例如 `V1.0.2__add_writing_module.sql`。
- 文件编码统一 UTF-8；**不要**在迁移脚本里写 `USE`、`CREATE DATABASE`、`DROP TABLE`、`LOCK TABLES`。

## 2. 新增表 / 改字段标准流程

### 2.1 标准指令话术（给 AI 编程工具）

> 项目使用 Flyway 管理数据库。请在 `<user-service|exercise-service|learning-engine-service>` 的 `src/main/resources/db/migration/` 新增迁移文件 `<V1.0.x__描述.sql>`，只写增量 DDL/DML；不要修改已应用的迁移文件；不要写 `USE`/`CREATE DATABASE`/`DROP TABLE`；字符集统一 `utf8mb4`，引擎统一 InnoDB，标识符用反引号；完成后运行对应模块的 `flyway:migrate` 并检查 `flyway_schema_history`。

### 2.2 执行流程

1. 确认目标库与模块（不要跨库）。
2. 新增迁移文件，例如：
   ```sql
   -- V1.0.2__add_writing_module.sql
   CREATE TABLE IF NOT EXISTS `writing_topic` (
     `id` BIGINT NOT NULL AUTO_INCREMENT,
     `title` VARCHAR(200) NOT NULL,
     `created_at` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
     PRIMARY KEY (`id`)
   ) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
   ```
3. 备份结构与数据（结构固定备份；数据类迁移另加一份含数据的备份）：
   ```bash
   scripts/backup-schema.sh
   ```
4. **窗口期检查（数据类迁移必做）**：若迁移是对同一行做"读-改-写"（`accepted_answers` 等），从生成快照到执行之间必须禁止自学习写入，否则快照之后的新增会被整体替换抹掉。详见 2.4-B。
5. 执行迁移：
   ```bash
   scripts/flyway.sh user-service migrate
   ```
6. 检查历史：
   ```bash
   scripts/flyway.sh user-service info
   scripts/flyway.sh user-service validate
   ```
7. 启动对应服务/跑测试，确认实体与表结构一致。
8. 提交：`feat(<module>): V1.0.x 新增 xxx 表`。

### 2.3 已应用迁移绝对不要改

Flyway 用 checksum 校验。已执行的 `V1.0.x` 文件一旦修改，`validate` 会失败，服务启动也会失败。
如果写错了：
- 未执行：直接改文件。
- 已执行：新增一个修复迁移（如 `V1.0.3__fix_xxx.sql`），不要改旧文件。
- 仅历史表损坏/手工改过库：用 `scripts/flyway.sh <module> repair` 修复历史记录，但**不会**修改表结构。

### 2.4 数据迁移口径约定（accepted_answers 类）

> 适用于 `patch-accepted-top200.mjs` / `generate-vocab-questions.mjs` 产出的所有 accepted 补丁迁移（V1.0.22 ~ V1.0.28）。

**A. 形态是「生成期并集 + 执行期整体替换」**

脚本在**生成时**读快照，算出 `现有 ∪ 候选`，把结果硬编码进：

```sql
UPDATE `question_info`
   SET `accepted_answers` = JSON_ARRAY(<生成时的并集>)
 WHERE `external_key` = '...' AND (... JSON_CONTAINS 守卫 ...);
```

执行时是**整列替换**。`JSON_CONTAINS` 守卫只用来判断"这条要不要执行"，**不防止覆盖**——它只检查新变体是否已存在，不检查数组里有没有别人后来加的值。因此措辞上不能写"并集写入"，那是生成期的动作，不是执行期的语义。

**B. 窗口期禁自学习（强制流程）**

从**生成快照**到**迁移执行**之间，必须停止 `JudgmentEngineImpl.saveAcceptedAnswer` 的写入（停服，或临时关闭自学习入口）。

原因：窗口期内用户答对被追加的 accepted 值不在快照里，执行时会被整体替换抹掉。执行前检查项：

1. 生成 `accepted-gaps.json` / 迁移 SQL 的时间点；
2. 确认该时间点到迁移执行之间没有自学习写入（`user_exercise_log` / accepted 变化可佐证）；
3. 有写入则**重新生成**，不要直接套用旧 SQL。

**C. accepted 生成规则三条（脚本与巡检必须同源）**

1. **不可数名词**不生成规则复数（`information` 不收 `informations`）；
2. **句中需要变形时不收原形**（正确答案是 `generalizations` 时，不收 `generalization`）；
3. **派生词、多音节形容词**只收原形，不生成比较级/最高级。

> 巡检判"缺失"必须用与生成器完全相同的规则，否则会把既定规则误报成缺失。历史教训：首版巡检误报 273 处，按真实口径修正后为 112 处。

**D. `word_dictionary` 口径：只作出题输入，判题不读**

- 判题链路只读 `question_content.correct_answer` 与 `question_info.accepted_answers`，**不查词库**；
- 词库缺词**不算** accepted 缺失；题目层用 `scripts/patch-accepted-top200.mjs` 的 `LEMMA_OVERRIDES` 兜底；
- **已定结论**：`awareness / study / important / become / emergence / sustainable / substantiated / unequal` 这 8 个词**不补词库**。依据：它们在 `6.26.sql` 的 `word` 表中存在，但 `book_word` 归属为 book 3（TOEFL）/ book 9，而 `scripts/import-words.mjs` 只认 `BOOK_CET4=7` / `BOOK_CET6=8`；强行补进去会让 `level` 字段失真，并让它们进入每日一词与词汇练习。

**E. 「accepted 只增不减」的例外**

默认规则是只追加合法变体、不删历史值。唯一的例外是**删除错误变体**，且必须同时满足：

1. 该变体经规则判定（如 `docs/review/tools/check-answer-slots.mjs` 的 `PSEUDO_FORM`）**并人工逐条复核确认**；
2. 迁移文件头**列出白名单**（题目 external_key + 变体 + 复核结论），一条 DML 只处理一个变体；
3. `WHERE` 以 `JSON_CONTAINS(accepted_answers, JSON_QUOTE('<变体>'))` 为守卫；
4. 用 `JSON_REMOVE(accepted_answers, JSON_UNQUOTE(JSON_SEARCH(accepted_answers,'one','<变体>')))` **定向摘除单个元素**；
5. **禁止整列重写、禁止按模式批量删**（例如 `WHERE accepted_answers LIKE '%er%'`）。

参考实现：`V1.0.29__remove_pseudo_forms.sql`（12 条白名单，6 行，全部带 `JSON_CONTAINS` 守卫，重复执行为 0 行）。

## 3. 与 Navicat 的分工

| 场景 | Flyway | Navicat |
|---|---|---|
| 新增/修改表结构 | ✅ 唯一入口 | ❌ 不要在共享库直接改 |
| 写入种子/字典数据 | ✅ 迁移脚本 | ❌ 不要手工插生产数据 |
| 临时查询、看数据 | — | ✅ |
| 本地实验性建表 | 可用临时库 | ✅ 仅限本地临时库 |
| 数据修复 | ✅ 写成幂等迁移 | ⚠️ 仅限本地排查，事后必须补迁移 |
| 备份/导出 | `scripts/backup-schema.sh` | ✅ 可视化导出 |

原则：**Navicat 可以看、可以查、可以本地试；共享库/生产库的结构变更只能走 Flyway。**

## 4. 换环境 / 部署如何保证 SQL 不遗漏

- 新机器/新库：
  1. 创建三个空库（或 Docker 自动创建）；
  2. 运行 `scripts/flyway.sh <module> migrate`，或直接启动服务让 Spring Boot 自动迁移；
  3. 检查 `flyway_schema_history` 每个版本 `success=1`。
- Docker：
  - `sql/flyway-init/00-create-databases.sql` 只建空库；
  - 各服务启动时 Flyway 自动迁移；
  - 不要再挂载/执行旧的 `sql/init/00-init.sql`。
- 发布前：
  - 对目标库执行 `scripts/flyway.sh <module> info`，确认没有 `PENDING`；
  - 先备份，再发布；
  - 迁移失败时服务应启动失败，不要绕过 Flyway 手工建表。
- 代码评审：
  - 每个新增表/字段必须同时有迁移文件；
  - 实体字段与迁移脚本必须一致；
  - 禁止只改实体不改迁移。

## 5. 回滚处理

Flyway Community **没有 undo**；MySQL DDL 也不能事务回滚。回滚策略：

1. **优先前向修复**：新增一个补偿迁移，把结构/数据改回目标状态。
2. **结构备份恢复**：用 `sql/backup/` 的 schema 备份恢复；数据恢复需额外全量备份。
3. **破坏性变更分两步**：
   - 第一步：停止写入/改名为 `_deprecated`，保留数据；
   - 第二步：确认无引用后，再新增迁移删除。
4. `flyway repair` 只修复历史表 checksum/失败记录，不是回滚工具。
5. `flyway clean` 已禁用（`clean-disabled=true`），禁止使用。

## 8. 禁止事项

1. 禁止修改已应用的 `V1.0.x` 迁移文件。
2. 禁止在共享库/生产库用 Navicat 直接改表结构。
3. 禁止在迁移脚本里写 `DROP TABLE`、`TRUNCATE`、`DELETE` 全表。
4. 禁止使用 `flyway clean`。
5. 禁止把 `sql/backup/` 提交到仓库。
6. 禁止只改实体不改迁移，或只改迁移不改实体。
